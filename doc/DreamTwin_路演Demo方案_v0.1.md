# DreamTwins 路演 Demo 方案 v0.1

> 文档状态：路演级 MVP Demo 基准版
> 版本：v0.1
> 上游文档：`doc/DreamTwin_产品说明书_v0.1.md`、`doc/DreamTwin_MVP原型方案_v0.1.md`
> 适用阶段：路演展示 / PRD 前置 / App 体验标准定义
> 当前补充口径：当前 App 骨架已升级为 `今日 / 梦境 / 消息 / 我的` 四 Tab 结构；路演 Demo 路径应从 `今日` 进入统一梦境地图，而不是直接从单一梦境日志开始。

## 1. Demo 定位

DreamTwins 的第一版 Demo 不应只是静态页面原型，而应该是一个路演级互动体验。

它的目标不是证明“这些页面能串起来”，而是让观众在 3-5 分钟内直观看到：

- DreamTwins 不是普通社交 App。
- DreamTwins 不是 AI 陪伴或 AI 代聊。
- AI 分身可以把用户的人格投影成可感知的关系预演能力。
- 梦境星图可以把关系机会呈现为可进入的梦境节点。
- 关系预告片可以降低真实关系开始前的不确定感。
- 双向梦境门可以把预演自然转化为真实聊天入口。

一句话目标：

> 让观众看到：这不是一份概念文档，而是一个有互动、有气质、能继续长成真实 App 的产品雏形。

## 2. Demo 载体

第一版 Demo 采用移动端 Web 实现，但体验标准按 App 来做。

### 2.1 为什么先做移动端 Web

- 便于快速开发和迭代。
- 便于路演投屏、录屏、分享链接。
- 便于后续迁移为真实 App 的产品结构。
- 便于在没有完整后端的情况下使用静态 Demo 数据跑通体验。

### 2.2 App-grade 标准

虽然第一版载体是 Web，但不能做成普通网页。

Demo 应按移动 App 体验设计：

- 移动端竖屏优先。
- 首屏必须有沉浸感。
- 页面切换要有状态和节奏。
- 梦境星图节点要可点击、可变化、可打开。
- AI 分身抽象投影要有存在感。
- 关系预告片要像“关系预告片”，不能像普通信息卡。
- 等待对方入梦和梦境门打开要有明确状态反馈。
- 真实聊天入口要让用户感觉关系真的可以开始。

## 3. 路演核心体验

路演 Demo 以“今日首页 + 统一梦境地图”为主舞台。

完整路径：

1. 用户进入 DreamTwins。
2. 首次用户创建 AI 分身；回访用户直接进入今日首页。
3. 今日首页展示关系动态、等待回应、梦境门和快捷入口。
4. 用户进入梦境 Tab / 统一梦境地图。
5. 梦境星图出现 3 个梦境节点。
6. 用户点击一个梦境节点。
7. 打开关系预告片详情。
8. 用户点击“想进入这个梦境”。
9. 节点进入“等待对方入梦”状态。
10. Demo 模拟对方确认。
11. 梦境门打开。
12. 用户进入真实聊天入口。

核心感受：

> 用户不是在刷人，而是在打开一段关系可能性。

## 4. 演示脚本

### 4.1 总时长

建议路演 Demo 控制在 3-5 分钟。

节奏分配：

| 阶段 | 建议时长 | 展示重点 |
| --- | --- | --- |
| 产品开场 | 20-30 秒 | 说明 DreamTwins 是 AI 关系预演社交 App |
| 分身生成 | 40-60 秒 | 展示 AI 分身抽象投影和人格摘要 |
| 梦境星图 | 45-60 秒 | 展示 3 个梦境节点和可点击互动 |
| 预告片详情 | 60-90 秒 | 展示关系预演如何降低破冰压力 |
| 双向梦境门 | 40-60 秒 | 展示等待对方入梦和梦境门打开 |
| 真实聊天入口 | 20-30 秒 | 展示从预演进入真人聊天 |

### 4.2 演示台词主线

开场：

> 传统社交把你推到一个陌生人面前，然后让你自己想第一句话。DreamTwins 做的是另一件事：在真实互动开始前，先让 AI 分身为你预演一段关系可能如何开始。

分身生成：

> 用户不是创建一个虚拟角色，而是在生成自己的人格投影。它不会替用户聊天，只会帮助用户看见关系可能性。

梦境星图：

> 昨夜，AI 分身带回了 3 段关系预告片。它们不是推荐流，也不是地图探索，而是 3 个可以进入的关系入口。

预告片详情：

> 用户点开后看到的不是资料卡，而是一段“如果我们相遇，可能会怎么开始”的关系预演。

双向梦境门：

> 用户想进入这段梦境，并不会立刻打扰对方。只有对方也确认进入，真实聊天才会开启。

真实聊天入口：

> 聊天不是从“你好”开始，而是从这段梦境留下的问题开始。

收束：

> DreamTwins 想改变的不是谁来替你社交，而是让真实关系有一个更自然、更有语境的开始。

## 5. 关键画面

### 5.1 首屏

目标：

- 30 秒内让观众知道产品是什么。
- 让观众感到这不是普通社交首页。

画面要点：

- 产品名 DreamTwins。
- 一句话定位：AI 关系预演社交 App。
- 背景有梦境空间感。
- 主按钮进入创建 AI 分身。

核心文案：

> 昨夜，你的 AI 分身遇见了谁？

### 5.2 AI 分身抽象投影

目标：

- 让 AI 分身有存在感。
- 避免虚拟伴侣、角色养成和换装感。

画面要点：

- 使用光影、颜色、轮廓和关键词表达分身。
- 分身名称和人格摘要同步出现。
- 生成过程要有轻微仪式感。

Demo 样例：

- 分身名称：雨天收藏家
- 投影色彩：雨蓝 + 暖橘
- 人格关键词：慢热、细节感、低压力、希望被理解
- 状态文案：适合从安静、具体、不催促的话题开始

边界：

- 不出现五官。
- 不出现服装。
- 不出现身体。
- 不出现等级、经验值、亲密度。
- 不出现换装或外观定制入口。

### 5.3 梦境星图

目标：

- 成为路演 Demo 的主舞台。
- 让观众直观看到 DreamTwins 的互动感。

画面要点：

- 3 个梦境节点浮现在星图中。
- 每个节点对应一条关系预告片。
- 节点可以点击。
- 节点状态会变化。

3 个节点：

| 节点 | 场景 | 对方代称 | 状态 |
| --- | --- | --- | --- |
| 节点一 | 雨夜便利店 | 玻璃橘子 | 未查看 |
| 节点二 | 凌晨海边电台 | 蓝色回声 | 未查看 |
| 节点三 | 月光候车厅 | 慢半拍旅人 | 未查看 |

状态变化：

- 未查看：微光节点。
- 已查看：节点变亮，保留读过痕迹。
- 等待对方入梦：节点缓慢呼吸。
- 梦境门打开：节点展开为门或光环。

边界：

- 不做自由探索。
- 不做路线移动。
- 不做真实地图。
- 不做附近的人。
- 不做关卡或任务。

### 5.4 关系预告片详情

目标：

- 让观众感到这不是资料卡，而是一段关系可能性的预告片。
- 让用户理解为什么值得亲自进入。

画面要点：

- 梦境场景标题。
- 模拟相遇片段。
- 可能聊到的话题。
- 共鸣或反差点。
- 真人进入建议。
- 主按钮：想进入这个梦境。

关键体验：

> 用户点开的不是一个人，而是一段关系如何开始。

### 5.5 等待对方入梦

目标：

- 展示 DreamTwins 的安全感。
- 证明真实互动不是单方打扰。

画面要点：

- 梦境节点进入等待态。
- 页面展示“等待对方入梦”。
- 明确说明不会发送真实消息。
- Demo 可模拟对方确认。

核心文案：

> 在对方确认前，你不会向对方发送任何消息，AI 分身也不会替你表达真实意愿。

### 5.6 梦境门打开 / 真实聊天入口

目标：

- 完成从关系预演到真实互动的转化。
- 让观众看到产品闭环。

画面要点：

- 梦境节点打开。
- 展示双方已确认。
- 出现真实聊天入口。
- 给出梦境引子作为第一句话。

核心文案：

> 接下来的每一句话，都由真人亲自发送。

推荐首句：

> 今天有没有一句你很想说，但最后没说出口的话？

## 6. Demo 数据

第一版路演 Demo 使用静态数据。

### 6.1 用户分身

| 字段 | Demo 值 |
| --- | --- |
| 分身名称 | 雨天收藏家 |
| 表达风格 | 慢热、细腻 |
| 社交节奏 | 慢慢熟悉 |
| 情绪状态 | 想被理解 |
| 关系偏好 | 低压力交流 |
| 投影色彩 | 雨蓝 + 暖橘 |

### 6.2 梦境节点

使用 MVP 原型方案中已经定义的 3 条关系预告片：

- 雨夜便利店 / 玻璃橘子
- 凌晨海边电台 / 蓝色回声
- 月光候车厅 / 慢半拍旅人

### 6.3 Demo 状态

必须支持的状态：

- 分身未生成
- 分身生成中
- 分身已生成
- 星图节点未查看
- 星图节点已查看
- 节点等待对方入梦
- 节点梦境门打开
- 真实聊天入口已开启

## 7. App-grade 体验标准

### 7.1 互动标准

- 所有关键节点必须可点击。
- 点击后必须有明确状态变化。
- 状态变化不能只靠文字说明。
- 页面之间要有连续性，不能像跳转 PPT。
- 梦境门打开必须成为演示高潮。

### 7.2 视觉标准

- 整体应有梦境感、空间感和微光感。
- 视觉不能过度游戏化。
- 视觉不能过度玄学化。
- 不能使用排行榜、任务、等级、抽卡等符号。
- AI 分身不能像可恋爱、可养成、可换装角色。

### 7.3 文案标准

- 文案必须服务真实关系开始。
- 文案不能制造命中注定感。
- 文案不能承诺关系结果。
- 文案不能暗示 AI 替用户完成社交。
- 每个关键按钮都要让用户知道下一步发生什么。

### 7.4 演示稳定性标准

- Demo 路径必须可重复跑通。
- 关键状态不依赖真实后端。
- 路演时不能出现空白页。
- 路演时不能出现无法解释的 loading。
- 断网情况下也应能完成静态演示路径。

## 8. 验收标准

Demo 完成后，必须满足：

- 观众能在 30 秒内理解 DreamTwins 是 AI 关系预演社交 App。
- 观众能看出 DreamTwins 不是普通资料卡社交。
- 观众能看出 AI 分身不是 AI 陪伴或虚拟伴侣。
- 梦境星图有明确互动感。
- 点击节点后能进入关系预告片。
- 点击“想进入这个梦境”后，节点能进入等待态。
- 模拟对方确认后，梦境门能打开。
- 用户能进入真实聊天入口。
- 关系预告片能让人感觉这段关系真的可能开始。
- 整体体验有路演展示的记忆点。

## 9. 后续衔接

路演 Demo 方案已被 PRD、需求池、技术方案和四 Tab App 骨架承接。当前下一步不是重新写 requirements-pool，而是继续做四 Tab App 骨架的本地 QA 与体验打磨：

1. 默认 `今日` 首页体验是否一眼懂。
2. 统一梦境地图是否同时承接新关系和好友共同入梦。
3. 消息-通讯录页是否只负责邀请与状态，不直接展示场景卡片。
4. 消息页是否只承接梦境门打开后的真人聊天。
5. 我的 Tab 是否只负责画像管理，不滑向陪伴或养成。

后续 PRD 与技术方案必须继续承接本方案中的路演级 Demo 标准，而不是只承接静态页面方案。

技术方案必须优先保证：

- 移动端 Web 优先。
- App 体验标准。
- 静态 Demo 数据可跑通。
- 梦境星图交互可演示。
- AI 分身抽象投影可演示。
- 路演路径稳定。

## 10. 当前结论

DreamTwins 的 MVP Demo 应该是一个能被路演、能被录屏、能被早期用户理解的产品雏形。

它可以先不是完整商业产品，但不能只是普通原型。

第一版最重要的展示目标是：

> 让观众亲眼看到，一段真实关系可以不从尴尬破冰开始，而是从 AI 分身带回的一段梦境预告开始。
