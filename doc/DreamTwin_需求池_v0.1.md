# DreamTwin 需求池 v0.1

> 文档状态：开发 Backlog 基准版
> 当前阶段：五区 App 骨架、Live AI adapter 和后端骨架已进入本地验收；下一步继续收稳真实 C 端体验
> 上游文档：`doc/DreamTwin_产品说明书_v0.1.md`、`doc/DreamTwin_MVP原型方案_v0.1.md`、`doc/DreamTwin_路演Demo方案_v0.1.md`、`doc/DreamTwin_PRD_v0.1.md`

## 1. 需求池目标

本需求池把 DreamTwin PRD 拆成可开发、可验收、可进入技术方案的 Backlog。

当前目标不是做报名材料，也不是一次性拼 Demo，而是为 DreamTwin 的真实 App 落地建立第一版执行清单。

第一版实现建议继续采用移动端 Web，但体验标准按 App 规划。

P0 标准锁定为：

> 视觉震撼优先，同时尽力跑通完整路径。

### 1.1 核心口径校准

当前 Backlog 的核心对象从“关系预告片”校准为 **AI 双人关系预演模拟**。

第一版仍然可以用短片化、分幕化方式展示，但需求拆解必须服务更深的产品内核：

- 模拟双方画像。
- 模拟相遇事件。
- 模拟可能对话和行为。
- 模拟关系发展路径。
- 输出恋爱可能、冲突风险、不好走向和建议动作。

“关系预告片”只表示展示包装，不再作为核心数据资产命名。

也就是说，第一版不能只是静态页面。它必须让用户和路演观众感到：

- DreamTwin 有梦境空间。
- AI 分身有存在感。
- `今日` 是已创建分身用户的默认首页，`分身` Tab 承接原 AI 分身主页管理能力。
- 用户可以从 `今日` 或底部导航进入梦境广场、好友邀请、消息和分身管理。
- 关系预演模拟不是普通文案卡片。
- 梦境节点可以被点击、进入、等待、打开。
- 最终可以走向真实聊天入口。

### 1.2 v0.2 产品升级方向

在 P0 主路径成立后，下一阶段 Backlog 增加三条正式验证方向：

- 风格化全身 3D AI 分身：让分身更像“网络世界里的你”，但不做写实脸、换装、等级或养成任务。
- 引导式 3D 梦境场景：让雨夜便利店、星空、海底、日料店、电影院、羽毛球场等场景成为关系预演舞台，但不做自由走路、地图拖拽、关卡或副本。
- 真实 AI 关系模拟：基于双方分身画像、场景事件和关系目标生成模拟结果，而不是只展示静态模板。

MBTI、血型、星座、玄学标签可以作为用户自愿填写的叙事信号进入画像，但不得包装成科学预测或命运判断。

## 2. 优先级定义

### P0：第一版必须完成

P0 是移动端 Web MVP / Demo 的最小可演示闭环。

P0 需求必须满足：

- 能进入后续技术方案。
- 能被拆成页面、组件、状态或数据任务。
- 能服务完整演示路径。
- 视觉完成度不能低到像静态草稿。
- 不依赖真实后端、真实用户关系发现或 AI 实时生成。

### P1：增强互动感和路演震撼感

P1 是在 P0 闭环基础上提升体验张力的需求。

P1 需求主要服务：

- 动效。
- 转场。
- 视觉节奏。
- 路演稳定性。
- 关系预演模拟的情绪和关系发展递进。

P1 不应该抢走 P0 的核心路径职责。

### P2：后续 App 化储备

P2 是未来真实产品化阶段的需求。

P2 不进入第一版移动端 Web MVP 的开发范围，除非后续重新调整路线。

P2 主要包括：

- 登录注册。
- 真实用户关系发现。
- AI 实时生成。
- 聊天后端。
- 推送。
- 审核。
- 数据分析。
- Native App 迁移。
- 真实好友系统和通讯录导入。
- 真实邀请链接或真实消息触达。

## 3. 需求条目结构

每条需求统一使用以下结构：

- 需求 ID
- 优先级

- 需求描述

- 依赖关系

- `DT-P0-001`
- `DT-P1-001`
- `DT-P2-001`

## 4. P0 需求

### DT-P0-001：移动端 Web App-grade 壳层

- 需求 ID：`DT-P0-001`
- 优先级：P0
- 所属模块：基础体验
- 用户目标：用户打开 Demo 时感到这是一个 App 雏形，而不是普通网页。
- 需求描述：搭建移动端 Web 单页体验壳层，按 App 比例、沉浸式首屏、固定底层状态管理和页面切换来组织体验。
- 验收标准：
  - 页面在移动端宽度下优先展示，适合手机竖屏演示。
  - 首屏不出现明显浏览器网页感或文档感。
  - 页面切换不刷新浏览器。
  - 所有核心页面能在同一条演示路径中连续访问。
  - UI 不出现文本溢出、遮挡或明显布局跳动。
- 依赖关系：无。
- Demo 价值：决定第一眼是否像一个可继续长成 App 的产品。

### DT-P0-002：静态 Demo 数据

- 需求 ID：`DT-P0-002`
- 优先级：P0
- 所属模块：数据基础
- 用户目标：用户能看到完整、稳定、可信的示例内容。
- 需求描述：基于 PRD 中的 `UserProfile`、`TwinProjection`、`DreamNode`、`RelationshipSimulation` 建立第一版静态 Demo 数据。前端类型和状态字段统一使用 `simulation` 语义。
- 验收标准：
  - 至少包含 1 个用户画像。
  - 至少包含 1 个 AI 分身抽象投影。
  - 必须包含 3 个梦境节点。
  - 每个梦境节点必须绑定 1 条关系预演模拟。
  - 每条关系预演模拟必须包含可能对话、关系发展路径、恋爱可能、冲突风险、不好走向和建议动作。
  - 数据能支持未查看、已查看、等待对方入梦、梦境门打开等状态。
  - 不接入真实用户关系发现、不接入 AI 实时生成。
- 依赖关系：PRD 数据结构。
- Demo 价值：保证演示不会依赖临场输入质量或网络生成结果。

### DT-P0-003：欢迎 / 产品解释页

- 需求 ID：`DT-P0-003`
- 优先级：P0
- 所属模块：首次体验
- 用户目标：用户在 30 秒内理解 DreamTwin 不是普通社交，也不是 AI 陪伴。
- 需求描述：实现欢迎页，解释 DreamTwin 的核心机制：先由 AI 分身预演关系，再由用户决定是否进入真实互动。
- 验收标准：
  - 页面明确表达“AI 关系预演社交”。
  - 页面能引导用户开始创建 AI 分身。
  - 不把产品说成 AI 陪聊、虚拟恋人、游戏或玄学占卜。
  - 视觉需要有梦境感和关系开端感。
  - 点击主按钮后进入 AI 分身创建页。
- 依赖关系：`DT-P0-001`。
- Demo 价值：建立产品心智，避免路演观众误解方向。

### DT-P0-004：AI 分身创建页

- 需求 ID：`DT-P0-004`
- 优先级：P0
- 所属模块：AI 分身
- 用户目标：用户能输入少量信息，感觉自己的关系偏好正在被理解。
- 需求描述：实现 AI 分身创建页，收集昵称、人格关键词、关系倾向、兴趣线索和可选依据。
- 验收标准：
  - 页面至少支持输入昵称。
  - 页面至少支持选择或输入人格关键词。
  - 页面至少支持选择关系倾向。
  - 页面说明 AI 分身用于关系预演，不是替用户聊天。
  - 主按钮能进入 AI 分身生成页。
  - 表单可以使用 Demo 默认值，避免路演输入耗时过长。
- 依赖关系：`DT-P0-001`。
- Demo 价值：让用户参与创建，从旁观变成进入体验。

### DT-P0-005：AI 分身生成与抽象投影

- 需求 ID：`DT-P0-005`
- 优先级：P0
- 所属模块：AI 分身
- 用户目标：用户看到一个有存在感的人格投影，而不是普通头像或聊天机器人。
- 需求描述：生成 AI 分身摘要和抽象投影预览，用昵称、人格摘要、颜色、光影、轮廓和关键词标签表达分身。
- 验收标准：
  - 展示 AI 分身昵称。
  - 展示人格摘要。
  - 展示关键词标签。
  - 展示抽象投影视觉。
  - v0.1 不出现写实五官、写实身体、服装、换装、等级或养成属性。
  - v0.2 可验证风格化全身 3D 分身，但不得出现写实真人脸、可替换服装、换装或养成属性。
  - 页面能继续进入 `今日` 首页，并可在 `分身` Tab 查看已保存分身。
- 依赖关系：`DT-P0-002`、`DT-P0-004`。
- Demo 价值：形成第一个震撼点，让观众感到 AI 分身存在。

### DT-P0-014：分身 Tab 管理页与 Demo 保存

- 需求 ID：`DT-P0-014`
- 优先级：P0
- 所属模块：AI 分身 / 主流程
- 用户目标：用户第一次创建分身后知道分身已保存，后续可在 `分身` Tab 查看和修改。
- 需求描述：实现 `分身` Tab 管理页，展示已保存的 AI 分身抽象投影、昵称、人格摘要、关键词和当前状态，并用本地 Demo 状态模拟“分身已保存”。
- 验收标准：
  - 首次生成 AI 分身后进入 `今日` 首页。
  - 刷新或后续打开 App 时，如已有分身状态，默认进入 `今日` 首页。
  - `分身` Tab 展示已保存分身，并提供修改分身能力。
  - 点击修改分身后进入 AI 分身创建页，修改后能回到生成页和 `今日` / `分身`。
  - 分身管理页不表现为 AI 陪伴页、角色养成页或虚拟形象管理页。
- 依赖关系：`DT-P0-002`、`DT-P0-005`。
- Demo 价值：让用户建立“分身已保存、后续可管理”的长期使用心智。

### DT-P0-015：五区导航入口主流程

- 需求 ID：`DT-P0-015`
- 优先级：P0
- 所属模块：主流程
- 用户目标：用户能通过 `今日 / 梦境 / 好友 / 消息 / 分身` 五区进入不同关系预演场景。
- 需求描述：通过底部五区导航和今日首页提供主要入口：`梦境` 用于查看昨夜 AI 已预演好的新关系入口，`好友` 用于发起已有好友的共同关系预演，`消息` 只承接梦境门打开后的真人聊天，`分身` 用于管理 AI 分身。
- 验收标准：
  - `梦境` Tab 能打开昨夜梦境日志和梦境星图。
  - `好友` Tab 能打开好友邀请页和邀请状态。
  - `消息` Tab 不提供普通开放私信入口。
  - 深层路径都能回到 `今日` 或统一梦境地图。
  - 两条路径都不接真实后端、不发真实邀请、不导入通讯录。
- 依赖关系：`DT-P0-014`、`DT-P0-006`、`DT-P0-016`。
- Demo 价值：覆盖“昨晚我遇见了谁”和“邀请好友一起梦境漫游”两个高价值 C 端使用场景。

### DT-P0-017：今日默认首页与五区 App 骨架

- 需求 ID：`DT-P0-017`
- 优先级：P0
- 所属模块：App 形态 / 首页
- 用户目标：用户每天打开 App 时先看到关系动态，而不是先看自己的分身。
- 需求描述：将 `今日` 设为已创建分身用户的默认首页，提供 `今日 / 梦境 / 消息 / 好友 / 分身` 五区导航，并将原 AI 分身主页能力收敛到 `分身` Tab。
- 验收标准：
  - 已创建分身的用户后续打开 App 默认进入今日。
  - 今日能承接 AI 已预演、等待对方入梦、梦境门打开、好友邀请、等待真人回应等关系动态。
  - 分身管理入口位于分身 Tab，不再作为每天默认首页。
  - 不引入内容流、普通开放私信或任务化首页。
- 依赖关系：`DT-P0-013`、`DT-P0-014`。
- Demo 价值：让 DreamTwin 更像独立 App，而不是单流程功能 Demo。

### DT-P0-006：梦境广场 / 昨夜梦境日志页

- 需求 ID：`DT-P0-006`
- 优先级：P0
- 所属模块：梦境日志
- 用户目标：用户能从 `今日` 或 `梦境` Tab 进入梦境广场，查看昨夜 AI 已预演好的关系入口。
- 需求描述：实现梦境广场 / 昨夜梦境日志页，作为进入统一梦境地图和新关系预演的首页。该梦境地图后续也必须被好友共同入梦路径复用。
- 验收标准：
  - 页面标题明确为昨夜梦境日志。
  - 页面出现 AI 分身简短摘要。
  - 页面出现 3 个关系机会的概览。
  - 页面能自然引出梦境星图。
  - 页面表达这是统一梦境地图，而不是只服务新关系的独立地图。
  - 好友共同入梦场景应来自同一套梦境地图 / 场景库。
  - 文案表达“这些是关系可能性的预演”，不是聊天记录。
- 依赖关系：`DT-P0-002`、`DT-P0-005`。
- Demo 价值：建立日常使用习惯和产品主场景。

### DT-P0-016：邀请好友梦境漫游

- 需求 ID：`DT-P0-016`
- 优先级：P0
- 所属模块：好友关系预演
- 用户目标：用户能邀请一个已有好友进入共同梦境场景，再一起查看关系可能如何变化。
- 需求描述：实现静态好友邀请闭环：选择 Demo 好友、发送一起入梦邀请、等待好友入梦、模拟好友接受、进入双人梦境广场入口、双方在统一梦境地图 / 场景库中共同选择入梦场景、进入共同梦境漫游预演。
- 验收标准：
  - 至少提供 1 个静态好友。
  - 至少提供海底探险、星际漫游、吃日料、看电影、看星空、打羽毛球等静态梦境场景。
  - 这些静态梦境场景必须来自梦境广场复用的同一套梦境地图 / 场景库。
  - 发送邀请后进入等待好友入梦页。
  - 等待页明确说明好友确认前不会发送真实聊天内容，也不会替用户表达关系意图。
  - Demo 能模拟好友接受邀请，并进入双人梦境广场入口。
  - 双方进入梦境广场后，再共同选择入梦场景。
  - 好友页不能直接用卡片列表选择场景。
  - 页面不能做成和梦境广场割裂的独立场景选择器。
  - 不接真实好友系统、不接通讯录、不生成真实邀请链接。
- 依赖关系：`DT-P0-002`、`DT-P0-017`。
- Demo 价值：补齐已有好友关系推进场景，让 DreamTwin 不只是陌生关系发现。

### DT-P0-007：梦境星图 3 个节点

- 需求 ID：`DT-P0-007`
- 优先级：P0
- 所属模块：梦境星图
- 用户目标：用户能通过点击梦境节点进入不同关系预演模拟。
- 需求描述：在昨夜梦境日志页中实现轻量梦境星图，展示 3 个梦境节点，并让每个节点可点击。
- 验收标准：
  - 梦境星图必须展示 3 个节点。
  - 每个节点必须对应一条关系预演模拟。
  - 节点至少支持未查看、已查看、等待对方入梦、梦境门打开状态。
  - 点击节点后进入关系预演模拟详情页。
  - 不支持自由探索、路径移动、地图闯关、附近的人或真实地理位置。
- 依赖关系：`DT-P0-002`、`DT-P0-006`。
- Demo 价值：形成 Demo 主舞台，让互动感不只停留在页面跳转。

### DT-P0-008：关系预演模拟详情页

- 需求 ID：`DT-P0-008`
- 优先级：P0
- 所属模块：关系预演模拟
- 用户目标：用户能看到 AI 对两个人相遇、对话、行为和关系发展的模拟，并判断是否想进入。
- 需求描述：实现关系预演模拟详情页，展示梦境标题、对方人格投影、双方画像建模、相遇事件、可能对话、关系发展路径、恋爱可能、冲突风险、不好走向、建议动作和当前节点状态。
- 验收标准：
  - 页面展示当前梦境节点状态。
  - 页面展示对方不是完整身份资料，而是关系预演中的人格投影。
  - 页面至少展示相遇场景、可能对话、行为预演、关系发展路径和关系模拟依据。
  - 页面必须展示恋爱可能和不好的走向，不能只展示正向结果。
  - 页面提供“想进入这个梦境”的主操作。
  - 页面提供返回梦境星图的路径。
- 依赖关系：`DT-P0-002`、`DT-P0-007`。
- Demo 价值：让“这段关系真的可能开始”的感觉成立。

### DT-P0-009：想进入梦境操作

- 需求 ID：`DT-P0-009`
- 优先级：P0
- 所属模块：关系确认
- 用户目标：用户能明确表达自己愿意让这段预演进入真实关系尝试。
- 需求描述：实现“想进入这个梦境”的操作，将当前节点从已查看或未查看推进到等待对方入梦状态。
- 验收标准：
  - 点击主按钮后进入等待对方入梦页。
  - 当前节点状态更新为等待对方入梦。
  - 页面反馈必须明确：用户不是在和 AI 聊天，而是在等待真实对方确认。
  - 不出现 AI 代替用户发送消息的表达。

## 8. P0 验收总标准

P0 完成后，DreamTwin 第一版移动端 Web MVP / Demo 必须满足：

- 用户能从欢迎页开始创建 AI 分身。
- 用户能看到 AI 分身抽象投影。
- 用户首次完成分身创建后进入今日首页。
- 已创建分身的用户后续打开默认进入今日首页。
- 原 AI 分身主页能力已收敛为分身 Tab 管理页。
- 用户能从今日或梦境 Tab 进入梦境广场。
- 用户能从好友 Tab 邀请好友梦境漫游。
- 用户能修改分身。
- 用户能看到今日首页承接等待、梦境门、好友邀请和聊天回访。
- 用户能进入梦境广场 / 昨夜梦境日志。
- 用户能看到梦境星图中的 3 个梦境节点。
- 用户能点击节点查看关系预演模拟。
- 用户能完成好友路径：选择好友 -> 等待好友入梦 -> 模拟好友接受 -> 双人梦境广场入口 -> 共同选择场景 -> 共同梦境漫游预演。
- 用户能选择想进入某个梦境。
- 用户能看到该节点进入等待对方入梦状态。
- 用户能看到关系状态进入双方已入梦状态。
- 用户能看到梦境门打开状态。
- 用户能进入真实聊天入口页。
- 观众能在 30 秒内理解 DreamTwin 是 AI 关系预演社交。
- 观众不会把 DreamTwin 误解为 AI 陪伴、游戏、地图探索或虚拟角色养成。

## 9. 当前不进入开发的内容

以下内容不进入 P0 或 P1：

- 真实登录注册。
- 真实用户关系发现系统。
- 真实好友系统。
- 通讯录导入。
- 真实邀请链接或真实消息触达。
- 后端分身持久化。
- 真实聊天后端。
- 生产级 AI 实时生成关系预演模拟。
- 真实地图。
- 可走地图。
- 附近的人。
- 角色养成。
- 换装。
- 虚拟伴侣能力。
- 付费系统。
- 审核后台。
- 推荐算法后台。

这些能力可以作为后续 App 化储备，但不能干扰第一版 MVP / Demo 的聚焦。

说明：`DT-P1-009`、`DT-P1-010`、`DT-P1-011` 是 v0.2 验证需求，不等于上线完整 3D 虚拟形象、自由 3D 地图或生产级实时 AI 系统。

## 10. 下一步

当前需求池已被技术方案、前端五区 App 骨架、Live AI adapter 和后端骨架承接。
